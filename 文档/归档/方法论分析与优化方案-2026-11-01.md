# 方法论内核分析与优化方案

> 分析对象：`00-核心机制`（协作 / 记忆 / 场景体系 / 派单）· `总纲.md` · `说明\记忆约定.md` · `12-源码照搬`
> 分析时间：2026-11-01 ｜ 依据：通读五篇机制 + 本次落地审计的实测证据

---

## 一、一句话内核

> **把"信任 AI 记得"换成"文件里可验证的落盘证据"；给每份文件指定唯一权威，并给它一个体量上限。**

这套方法论真正解决的不是"AI 能不能干活"，而是**"三个月后第 11 个会话还能不能接上"**。
所有具体规矩（4 KB、五档修改权、≤3 条消息、`【结束】`）都是这条内核在不同事故上的投影。

---

## 二、内核的七条不变量

| # | 不变量 | 出处 | 它在保护什么 |
|---|---|---|---|
| 1 | **记忆在文件，不在会话** | 二·§1 | 会话是易耗品；价值 = 产出文件，不是聊天长度 |
| 2 | **单一权威**：一个事实只存一处，别处只放指针 | 二·§9「两份数字打架」· 总纲「每个东西只属于一层」 | 防"记忆说 A、台账说 B" |
| 3 | **分层 + 体量红线**（注入 / 私有 4 KB / 项目 8 KB / 主文件 25 KB） | 二·§2、§6 | 上下文经济学：谁读、多久读一次，决定它能有几个字节 |
| 4 | **主权与合法性**：规则只认机主；场景只写自己；修改权分五档 | 一·§1、§2 | 防"规矩自己长"——今天加一条，三个月后不知哪条是真的 |
| 5 | **闭环要证据**：派单≠公告；回执四件套；结论必须带落盘路径 | 一·§4、§5 ｜ 四·§3、§4 | 防"活干完了但对方不知道"= 没干完 |
| 6 | **反例验收**：校验工具必须能证明"该失败时会失败" | 总纲·规矩怎么守 ｜ 二·§6 | 防"工具全绿但其实什么都没查" |
| 7 | **归档只进不改** | 总纲·L5 | 任何升级都能回滚 |

**内核的形状**：前三条管"记忆不丢"，第 4 条管"权力不烂"，第 5～7 条管"结果可信"。
三者缺一，另两者都会退化——这正是 `00-核心机制/README.md:14-15` 自己写下的判断。

## 三、内核的四层结构（按"可执行程度"重排）

方法论自己按"内容"分层（宪法 / 共享 / 私有 / 个人 / 运行时 / 归档）。
但如果按**能不能被机器强制**来看，它实际是四层，且**越往下越薄**：

```
L1 宪法层   全局铁律、修改权分档、主权         ← 文档最厚，机器强制最少
L2 机制层   交接协议、派单状态机、换会话协议     ← 文档中等，靠 AI 自觉执行
L3 抓手层   场景记忆.mjs / 发布前检查.mjs / sessions.mjs ← 工具最薄，只有 4 个脚本
L4 实例层   场景 json、sessionId、路径常量      ← 无任何校验，全靠手填
```

**这张图就是优化的靶心**：L1 写得极好、L2 写得很好，但 **L3 只覆盖了 L2 的一小部分，L4 几乎裸奔**。
本次审计的全部缺陷，没有一条是"宪法写错了"，**全部落在 L3/L4**。

## 四、六个结构性张力（诊断，不是复述）

### T1 换会话协议**反自己**：要求"同步三处"，而内核要求"单一权威"

`二·§7` 第 ③ 步明文要求同步 **① 场景配置 sessionId ② 身份索引会话 id 列 ③ §〇 交接署名**。

- 这**正是**它在 `二·§9` 里列为失效模式的"同一事实存在两处"。
- 现状是**靠纪律同步**，而纪律没有抓手 ⇒ 本次实测中 `_场景身份索引.md` 与 4 份 json 恰好一致，靠的是人没漏；漏了也**没有任何工具会发现**。

### T2 判据在文档，执行在工具，**二者之间没有一致性验收**

方法论要求"反例验收"，但**只对自己造的校验工具**要求，没要求"工具实现 = 文档判据"。
实测后果（三条，均为本次审计证据）：

| 文档判据 | 工具实现 | 后果 |
|---|---|---|
| 会话必须在库（换会话前置） | `场景记忆.mjs:471` 把库拼成 `.dsh\.dsh\sessions` | **恒假警告**，真丢会话也照样绿 |
| 记忆唯一真源 | `init` 同时产出 `场景私有记忆.md` 与 `X场景私有记忆.md` | 磁盘上出现 **3 组逐字节重复** |
| 端口 3083 | `sessions.mjs` / `会话改名` / `归档会话` 仍写死 3080 | 引擎起来后这三个脚本默认连不上 |

### T3 **没有"模板 → 实例"这道工序**（本次审计 M1/M2 的真正根因）

内核假设了"文件 = 权威"，但**没区分两种文件身份**：

- **模板文件**（要公开、必须是占位符、`README.md:40` 明说"照抄一定失败"）
- **实例文件**（要能跑、必须是本机真值、含真实 sessionId）

二者**共用一个工作树、共用 .git、被同一批 commit 跟踪**。于是"落地"必然等于"把脱敏位填成真值"，
而"填真值"必然触发 `发布前检查` 的 13 处红线 —— **落地动作与出包闸门天然对立**。
这不是谁犯了错，是**缺了一道工序**。

### T4 红线只管**体量**，不管**可开工性**

`二·§6` 定了 4 KB / 8 KB / 25 KB，工具也只量字节（`check` 输出「§〇 449 B」）。
而 `二·§9` 自己已经写下这个漏洞：

> 「**体积正常但内容没用** —— 只盯体量，不看"读完能不能开工"」

现状正是如此：4 个场景 §〇 都是 449 B 合规，但内容是「（新场景，还没有交接记录）」+ 核心职责「（待补）」。
**红线全绿，记忆为零。**

### T5 合法性收紧到"只认机主"，但没给"待确认"一个落点

`一·§1` 规定极其正确：AI 发现该加规矩时**不许自己加**，只能写进「待机主确认」清单。
但**这个清单没有工具、没有路径、没有格式**（只有一句示意）。结果是两种退化：
要么 AI 干脆不提（判断流失），要么提在聊天里（就消失了）。**这是内核最贵的一条规矩，却最没有抓手。**

### T6 文档自身口径漂移（违反它自己的单一权威）

同一个"场景记忆放哪"，仓库存了两套说法：

| 出处 | 说法 |
|---|---|
| 根 `README.md:193`、`00-核心机制/二-记忆机制.md:227`、`二-记忆机制.md:69` | **`引擎\场景记忆\<场景>\`** |
| `12-源码照搬/README.md:54`、`说明\记忆约定.md:8`、实际磁盘 | **`引擎数据\.dsh\场景记忆\`** |

读者按前者建目录，工具按后者读，`总纲` 用第三种叫法（`引擎\场景记忆`）。**内核在文档层就破了自己的规矩。**

## 五、优化方向与方案（按 ROI 排序）

> 每条都自带**验收判据**——沿用方法论自己的"反例验收"：**不能证明会失败的工具，等于没做。**

### O1 ★★★ 把判据变成"可执行断言"，并给每条断言配反例样本

**问题**：T2 —— 判据散在文档，工具各写各的，跑绿了不能证明对。

**方案**：新增 `工具\体检.mjs`，只做一件事——**跑断言、出差异集合**，不修。首批 8 条：

```
A1 路径口径一致：代码里出现的记忆根 == 实际存在的那一个
A2 端口单一来源：所有脚本的端口都从 DSH_PORT / 一个常量读
A3 记忆单真源：每个场景目录下 X场景私有记忆.md 与 场景私有记忆.md 不得同时存在
A4 会话在库：每个 sessionId 能在 sessions\<ws>\<id>\ 找到（修掉 .dsh\.dsh）
A5 会话 cwd 有效：会话记录的 cwd 目录必须存在
A6 面板映射齐：每个 harness 面板都有 HANDOFF 映射，且映射路径存在
A7 §〇 可开工：见 O4
A8 实例化未泄漏：模板模式下不得出现真实 sessionId / 本机绝对路径
```

**验收判据**：仓库内建 `工具\_反例\` 目录，每个断言配一份**故意坏掉**的 fixture；
`体检.mjs --self-test` 必须做到"8 条断言在坏样本上全部报错、在好样本上全部通过"。
**有一条断言在坏样本上没报错 ⇒ 这条断言作废。**

**成本**：约 1 天。**收益**：本次审计的 6 类缺陷全部变成"提交前必拦"。

### O2 ★★★ 引入实例清单，把"模板/实例"变成两道工序

**问题**：T3 —— 落地与出包天然对立。

**方案**：
1. 新增 **`工作台.json`（实例清单，唯一真值来源）**：`{ root, dshPort, sitePort, engineSource, sessions:{命令:"session-…",B站:"…"} }`。
2. 代码**只读清单**，不再把真值写进被跟踪的源文件：`main.js` 读 `工作台.json`，`scenarios/*.json` 的 `sessionId` 由 `工具\实例化.mjs` 在运行前注入（或留 `__待填__` 并允许清单覆盖）。
3. `工作台.json` 进 `.gitignore`；仓库内只保留 `工作台.example.json`。
4. `发布前检查` 增加 `--mode template|instance`：模板模式**必须**零真实 id；实例模式把"含真实 id"从红线降为**预期项**（只警告不拦）。

**验收判据**：
- 干净 clone → `node 工具\实例化.mjs --dry` 能列出"要填 4 个 sessionId + 1 个 root"，**不需要人读文档猜**；
- 模板模式下 `发布前检查` 通过、`体检 A8` 通过；
- 实例模式下 `发布前检查` 不再因真实 id 报红线（红线只对"要出包"生效）。

**成本**：1～2 天（要改 `main.js` 与 3 个脚本的取数点）。**收益**：解除"落地即违规"，并让"公开版"与"我的实例"真正共用一套代码。

### O3 ★★ 消灭"同步三处"：sessionId 单源派生

**问题**：T1 —— 协议要求三处同步，内核要求单一权威。

**方案**：
- **唯一源**：`scenarios/<id>.json` 的 `sessionId`（或 O2 的 `工作台.json`）。
- `_场景身份索引.md` 的会话 id 列改为**工具生成**（`身份索引.mjs --stamp`），文件头标"本表由工具生成，手改即校验失败"——与 `身份卡.md` 同一套做法（这条方法论已经有先例，照抄即可）。
- `§〇` 的交接署名由 `交接` 子命令写入（现在是人写）。

**验收判据**：改一次 `sessionId`（只改一处）→ 跑 `体检`，三处应自动一致；
刻意只改两处 → `体检 A4/A6` 必须报"索引未回填"。

**成本**：半天。**收益**：换会话从"记得同步三处"变成"改一处 + 跑一次"。

### O4 ★★ 给 §〇 加"可开工性"判据（4 KB 之外的第二道闸）

**问题**：T4 —— 红线全绿但记忆为零。

**方案**：`check` 增补四条**结构性**判据（都可机器判）：

| 判据 | 机器怎么判 |
|---|---|
| §〇 只含 5 小节，且顺序固定 | 正则数 `### 1)`～`### 5)` |
| 「下一步」非空且是"动词 + 对象" | 非空 + 不以「（待补）/ 无 / —」开头 + 长度 ≥ 8 字 |
| 「卡点」必填（无则写"无"） | 节内非空 |
| §〇 不得含过程流水（周报化） | 禁止出现「今天/然后/接着」≥3 次；单节 ≤ 15 行 |

外加一条**语义抽查**（人能判、工具只提示）：`§〇` 里必须能回答"我是谁 / 干到哪 / 下一步 / 卡在哪"四个问句——工具检查这四个关键词各自的落点是否存在。

**验收判据**：拿一份真实的"周报式 §〇"做 fixture，`check` 必须报红（现在会绿）。

**成本**：半天。**收益**：把 4 个空壳场景直接标红，逼出"（待补）"的替代。

### O5 ★★ 给"待机主确认"一个真实落点

**问题**：T5 —— 最贵的规矩没有抓手。

**方案**：新增 `引擎数据\.dsh\场景记忆\_共享记忆\待确认.jsonl`（**append-only**）+ `工具\待确认.mjs`：

```
node 工具\待确认.mjs add --内容 "…" --为什么 "…" --依据 "…"   # AI 只能追加
node 工具\待确认.mjs list                                      # 机主随时看
node 工具\待确认.mjs 转正 <id> --条款 "<正式条文>"              # 只有机主能做
```

`转正` 时由工具把条文**写进 `05-协作与规矩`**并留痕（谁、何时、原提议）。
**验收判据**：`add` 不给 `--依据` 必须拒绝；`转正` 必须产生一条 `_审计\规矩变更.jsonl`。

**成本**：半天。**收益**：把"不许自己加规矩"从**禁令**变成**通道**——禁令没有通道，只会被绕过。

### O6 ★ 上游差异分类器（把刚做的闸门升级）

**问题**：现在的 `同步上游.mjs` 只说"改了哪些文件、多少行"，不说"该不该并"。

**方案**：给每个改动路径打**层标签**，输出三档建议：

| 层 | 例子 | 建议 |
|---|---|---|
| 宪法层 | `05-协作与规矩/`、`00-核心机制/` | ⚠ 须你本人评审（规矩变更） |
| 实例层 | `scenarios/*.json`、`工作台.json`、`*.vbs` | ⚠ 与你本机配置冲突，需人工合并 |
| 其余 | 文档、配图、`13-公开情报` | ✅ 可直接并 |

**验收判据**：`同步上游.mjs` 对本次那 2 个提交应分别输出「实例层 ⚠」与「实例层 ⚠」；
用一个纯文档提交做反例，应输出「✅ 可直接并」。

**成本**：2 小时。**收益**：把"看一眼再决定"从人工判断变成有依据的初筛。

### O7 ★ 文档口径收敛（一次性）

**问题**：T6 —— 三套叫法。

**方案**：以**实际磁盘**为准统一为 `引擎数据\.dsh\场景记忆\<场景>\`。
实测命中「`引擎\场景记忆`」旧口径的共有 **6 份文档 / 12 处**（本次已核过行号）：

并在 `说明\记忆约定.md` 顶部加一句「本口径为唯一口径，其它文档如有冲突以本文件为准」。

**验收判据**：`grep "引擎\\\\场景记忆"` 全仓命中 0（除历史归档与 `场景记忆\*\场景画像.md` 这类生成物）；

**成本**：1 小时。**收益**：让"单一权威"在文档层不再破例。

## 八、不要做什么（守住它最值钱的部分）

这套方法论最值钱的**不是**那些数字（4 KB / ≤3 条 / 五档），而是三件事：

| 值得保留 | 为什么 |
|---|---|
| **判据式表达**（"一句话判据"代替长清单） | 可被 AI 直接用于判断，不占上下文 |
| **失效模式表**（症状 → 根因 → 修法） | 每条都可回溯到真实事故，是可信度的来源 |
| **「最小可用」分级**（1～2 个会话别全抄） | 让它保持"可抄"，这是它传播力的根 |

因此优化必须遵守一条约束：**新增的每一条机制，都必须同时给出"什么时候不该用它"**。
否则就是在给一套本来靠"轻"取胜的方法论**加钢筋**——加到最后，没人再抄得动。

> 反例警示：`05-协作与规矩/二-标准化规范.md` 已 **103.6 KB**、`三-跨场景协作.md` 已 **59.6 KB**。
> 这两份**恰好是"按节号查、不注入"的细则层**——它们不是错，但**它们已经涨到没人会通读**。
> 优化时不要再往这两份里加东西；新机制一律走 `工具\` + 一页判据。
