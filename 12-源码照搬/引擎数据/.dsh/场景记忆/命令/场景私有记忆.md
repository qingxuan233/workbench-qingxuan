## 五、坑与决策

- （只追加）
- **2026-11-01 临时目录不可写 → 所有命令类工具瘫痪**（只读工具正常，`read/write/edit` 可用）
  - 现象：`pwsh` 报 `CreateFileW failed (Win32 5)`（Win32 5 = ERROR_ACCESS_DENIED）；`glob`/`grep` 报 `ripgrep launch failed`。
  - 关键实测：用 `write` 工具往 `%TEMP%\dsh-acl-locks\` 建文件同样 `EPERM ... mkdir`；而写工作区 `D:\...\default-workspace` 成功。**说明不是 pwsh、不是 ripgrep、也不是 ACL 沙箱的问题，而是 `C:\Users\69559\AppData\Local\Temp` 对当前进程整体不可写。**
  - 目录里残留 `b6c1b3663f2595d1.lock`（可读、0 字节），说明临时目录**曾经可写**，是后来被改掉权限/被防护软件锁死的。
  - 调用链（源码定位）：`pwsh` → `dsh-subprocess-local` 在 tmpdir 建 `dsh-subprocess-XXXXXX`（mkdtemp，EPERM）→ 沙箱后端 `dsh-sandbox-windows-acl` 的 `withPathLock()` 还要在 `%TEMP%\dsh-acl-locks\` 建锁文件（CreateFileW，ACCESS_DENIED）。两级都要写临时目录，所以必然失败。
  - 连带后果：`grep`/`glob` 底层是 ripgrep 子进程，一并失效 → 检索只能逐段 `read` 源码。
  - 结论：**在临时目录恢复可写之前，任何"启用命令类工具"的尝试都不会成功**，这不是配置开关问题（沙箱模式已试过 workspace-write 与 danger-full-access，均失败）。
 - **2026-11-01（复验，用户又一次要求"尝试启用命令类工具"）**：结论未变，但定位更精确。
   - `pwsh`（workspace-write）→ `CreateFileW failed (Win32 5)` @ `%TEMP%\dsh-acl-locks\b6c1b3663f2595d1.lock`
   - `pwsh`（danger-full-access 单次重试）→ `EPERM mkdtemp 'C:\...\Temp\dsh-subprocess-XXXXXX'` —— **跳到沙箱之前就死在 mkdtemp**，证明不是 ACL 沙箱导致，是临时目录本身拒绝创建目录。
   - `glob` → `ripgrep launch failed`（同因：子进程也要 mkdtemp）
   - `read`/`write`/`edit` 正常；`read` 工作区外文件正常（`.lock` 文件已不存在，说明有人清理过 Temp，但目录仍不可建子项）。
   - 关键新判断：**连 `danger-full-access` 都失败，等于 DSH 侧所有开关已试穿**。剩下唯一可能是宿主机层面（Temp 目录 ACL / 杀软 / 组策略 / 磁盘满）。要修只能在 DSH 之外动手（PowerShell 手动 `icacls`，或临时目录换到工作区 `TMPDIR`/`TEMP` 环境变量），本场景工具链无法自我修复。
   - 给下一位的实操建议：让用户在普通 CMD/资源管理器里 `icacls "C:\Users\69559\AppData\Local\Temp"` 看权限，并 `del /q` + 重建 Temp；或直接改 DSH 启动时的 `TEMP`/`TMP` 环境变量指向可写目录。
 - **2026-11-01（第三轮复验，文件策略已切到 danger-full-access、审批策略 never 之后）**
   - `pwsh` 仍 `EPERM mkdtemp %TEMP%\dsh-subprocess-XXXXXX`；`grep` 仍 `ripgrep launch failed`。
   - 决定性对照：`write` 往 `%TEMP%` 写**文件**和**目录**均 `EPERM mkdir`（写入实现会先建 `.dsh-probe-*.tmpdir`），而同一 `write` 到工作区 `D:\...\default-workspace` 成功。
   - 由此**排除 DSH 沙箱**：danger-full-access 下文件策略已不限制，Temp 依然不可建子项 → 阻塞在宿主机 Temp 目录本身。
   - **给用户的唯一可行修法（按优先级）**：① 退出 DSH，在「系统属性 → 环境变量」把用户级 `TEMP`/`TMP` 改到 `D:\Temp` 等可写目录后重启 DSH；② 或在管理员 CMD 里 `icacls "%LOCALAPPDATA%\Temp" /grant "%USERNAME%":(OI)(CI)F`；③ 检查杀软/组策略是否锁 Temp。
   - 现状口径：**命令类工具（pwsh / glob / grep）在 Temp 修复前不可启用，且无法在会话内自愈**。
 - **2026-11-01 第五轮：已恢复！根因是「临时目录根」，不是「Temp 目录权限」——前四轮的结论有一半是错的**
   - 实证：`pwsh` 直接成功；`$env:TEMP` = `E:\git_code\DeepSeek Harness\workbench\12-源码照搬\外壳\data\temp`（DSH 自己的临时区，**不在 C 盘**）；PowerShell 5.1.26100.9711。
   - 真相：前四轮报错路径都是 `C:\Users\69559\AppData\Local\Temp\...`，说明当时 DSH **没用自己的临时区**、退回了系统 Temp，而系统 Temp 不可建子项 → 全部命令类工具死。现在 DSH 用 `外壳\data\temp`（可写）→ 一切正常。
   - **教训（重要，别再走弯路）**：判断"是不是 Temp 坏了"时，先跑一句 `$env:TEMP` 确认 DSH 实际用的临时目录，**不要只看报错里的路径就断定是系统的 Temp**。修法永远优先是"让 DSH 用可写的临时目录"，而不是去改系统 Temp 的 ACL。
   - 另一个连带发现：工作区 `D:\...\default-workspace` 里累积了探测文件 `_dsh_probe.txt` / `.write-probe.txt` / `.dsh-probe-test.txt` / `.dsh-probe-2.txt` / `.probe-3.txt`（前两个不是我建的），已清理。
   - `grep` 报 `os error 3 系统找不到指定的路径` 于 `D:\Programs\DeepSeek Harness\resources\app.asar\dsh`：**那是实现 checkout 路径失效（app.asar 是打包文件、不是目录），不是工具故障**。grep 能力本身正常。
   - 现状态：**pwsh / glob / grep 全部可用**。教训同样适用于 `command` 场景之外的任何"工具坏了"判断：先分清「工具挂了」和「我传的路径/环境不对」。
