# 部署到另一台机器

> 想让 AI Agent 自己照做：看仓库根目录的 [AGENTS.md](../AGENTS.md)（命令 + 期望输出 + 失败分支）。
> 人工照着做就用本文。

> 这台工作台的设计前提：**记忆在文件里、不跟着会话走**。所以换机器时，
> 真正要带走的是仓库（记忆 + 场景 + 外壳 + 工具），不是会话。

---

## 一、前提

| 需要 | 说明 |
|---|---|
| Windows | 外壳是 Electron 应用，启动脚本是 VBS/BAT |
| Node.js 18+ | 工具链、外壳依赖安装、脚本都靠它 |
| DSH 引擎（可选） | 只影响 AI 面板；没装也能启动界面，只是面板不能用 |

---

## 二、四步装好

```powershell
git clone https://github.com/qingxuan233/workbench-qingxuan.git
cd workbench-qingxuan\12-源码照搬

# 1) 装依赖 + 清残留 + 生成本机清单（首次约 200 MB，慢属正常）
node 工具\初始化.mjs --install

# 2) 启动（双击也可以）
.\启动.bat

# 3) 五个场景各点一次 AI 面板（会按当前工作区建会话），然后回填：
node 工具\实例化.mjs --apply

# 4) 验收
node 工具\体检.mjs
```

第 4 步期望：**15 绿 · 0 红 · 0 待办**。
刚做完第 1 步时是 15 绿 · **2 待办**（会话库与会话绑定），那是正常中间态。

## 三、换机器时什么跟着走、什么不跟

| 东西 | 跟仓库走？ | 原因 |
|---|---|---|
| `引擎数据/.dsh/场景记忆/`（记忆、身份卡、索引） | ✅ 跟 | 记忆在文件里，这是这个工作台的核心资产 |
| `外壳/scenarios/*.json`（场景与面板） | ✅ 跟 | 但里面的 `sessionId` 是占位符 |
| `外壳/`、`工具/`、文档 | ✅ 跟 | 代码与规矩 |
| `工作台.json`（本机清单） | ❌ 不跟 | 含本机引擎路径与会话 id；由 `初始化.mjs` 重建 |
| `引擎数据/.dsh/sessions/`、`storages/` | ❌ 不跟 | 会话与工作区缓存是可弃的运行状态 |
| `引擎数据/.dsh/.credentials.yaml` | ❌ 不跟 | 登录凭据只属于当前机器 |
| `外壳/node_modules/` | ❌ 不跟 | 用 `--install` 重装 |

## 四、路径为什么不会错

代码里**没有任何一个写死的盘符**。所有根目录从两处推导：

1. 主进程：`path.dirname(__dirname)`（外壳所在目录）+ `工作台.json` 的 `root`（默认 `null` = 跟随）
2. 渲染层：`location.pathname` 里反推 `<根>\外壳\renderer\`

所以仓库放在任意盘符、任意目录（包括用户目录下），都不用改一行代码。
搬到别的机器后如果发现某处报「路径不存在」，那一定是漏了个兜底 —— `体检` 会指出来。

## 五、出包给别人（另一种需求）

自己在几台机器之间搬，用上面的流程就够了，**不要把 `工作台.json` 和记忆打包出去**。
如果确实要给别人一份干净的模板：

```powershell
node 工具\初始化.mjs --hard        # 连凭据一起清
node 工具\发布前检查.mjs --mode template   # 必须 0 命中
```

`--mode template` 会把「本机绝对路径 / 真实会话 id」都当红线 —— 这是刻意的闸，不是 bug。
## 如果双击后没有任何反应

先看 `外壳\data\startup.log`。最常见的一种原因已经内置自愈，说明如下：

部分机器（受组策略、杀毒、权限限制）上 Chromium 的沙箱初始化会失败，Electron 以
`-2147483645`（即 `0x80000003`，STATUS_BREAKPOINT）立即退出，窗口一次都不出现，
看起来就是"双击没反应"。

`启动.bat` 的处理是：先按正常方式启动；失败后自动改用 `--no-sandbox` 再启动一次；
一旦发现退出码正是 `-2147483645`，就在 `外壳\data\no-sandbox.flag` 记一笔，
以后这台机器直接走兼容模式，不再白失败一次。

代价要说清楚：`--no-sandbox` 关掉了 Chromium 的进程隔离。对本工作台这种
"只加载本地页面 + 本地引擎"的用法风险可控；如果你介意，可以删掉
`no-sandbox.flag` 并想办法让沙箱正常工作（常见办法是以普通用户身份运行，
不要用管理员权限启动）。
## 第一次启动该看到什么（判据清单）

排查不要靠"感觉"，按下面这几条对照。每一条都有明确的证据位置。

| 时刻 | 应该看到 | 证据在哪 |
|---|---|---|
| 双击后 0～1 秒 | 出现一个控制台窗口，打印「正在启动工作台…」 | 控制台本身 |
| 约 0.5 秒 | 主窗口出现，标题 `DSH 引擎 · 清玄的工作台` | 任务栏 / 窗口标题栏 |
| 约 3 秒 | 界面加载出内容，顶栏四个场景标签齐全 | 界面 |
| 任何时候 | 控制台窗口自己关掉 | — |

对应到日志：

- `外壳\data\startup.log` —— 启动器自己的流水账（会自管：超过 256 KB 轮转成
  `startup.log.prev`，只留一份）。正常长这样：

       [start] 周日 2026/11/01 20:59:53.37
         exe = ...\外壳\node_modules\electron\dist\electron.exe
         out = ...\外壳\data\startup-out-<随机>.log
         log = ...\外壳\server.log (offset 137053)
       [compat] no-sandbox.flag found
       [run] electron --no-sandbox . 20:59:53.42
       [exit] rc=0 21:00:16.74 window-visible + engine ready

  出现 `[compat] ... found` 说明这台机器之前判定过沙箱起不来，走的是兼容模式；
  出现 `[retry] ... retry with --no-sandbox` 说明这次刚判定出来（会重试一次）；
  出现 `[skip] port 3083 already listening` 说明工作台已经开着，本次没有再拉一个；
  出现 `[fail] ...` 说明两次尝试都没看到窗口，控制台会打印诊断并停住。

  判据看**本次**：启动器先记下 `server.log` 的长度（上面的 `offset`），只认这个
  偏移之后新写进去的 `window-visible`。这样上一次成功过的日志不会把这一次的失败
  伪装成成功。

- `外壳\data\startup-out-<随机>.log` —— 这一次 Electron 进程的 stdout/stderr。
  成功时自动删掉；失败时保留，并另存一份 `startup-fail.log`（下次失败时覆盖），
  目录里始终只有一个本次的输出文件。

- `外壳\server.log` —— 外壳主进程的日志（超过 4 MB 轮转成 `server.log.prev`）。健康的两行是：

       [boot] window-visible ms=4xx
       engine ready in x.xs via DSH 官方 CLI

  只有 `window-visible` 没有 `engine ready` ⇒ 窗口起来了但引擎没起来，界面会是白的。

判断"到底起没起来"的硬标准就一条：**本次启动之后** `server.log` 里有没有 `window-visible`。
启动器失败时会把 `startup-out-<随机>.log` 和 `server.log` 尾部一起打印出来，
照那个发出来就能定位。

### 三种"看起来一样、其实不同"的故障

| 现象 | 真因 | 特征 |
|---|---|---|
| 双击完全没反应，连控制台都没有 | 依赖没装（没有 Electron） | 会弹「需要装依赖」提示；`外壳\node_modules` 不存在 |
| 双击有控制台，但一闪就没、窗口从不出现 | Chromium 沙箱初始化失败 | 退出码 `-2147483645`（`0x80000003`）；换成 `--no-sandbox` 就能起 |
| 窗口出现，但内容区一片白 | 引擎没起来 | `server.log` 有 `window-visible`、没有 `engine ready`；`startup-out-*.log` 里常有 `不是内部或外部命令` 或 `spawn ... ENOENT` |
